A minimal authenticated task manager built for the assignment using **Node.js + Express + MongoDB + React/Vite**.

## 2. Why this architecture?

### Backend

- **`routes/`** only defines HTTP endpoints and middleware order. This keeps routing readable.
- **`controllers/`** translates HTTP requests into service calls and responses. Controllers intentionally stay thin.
- **`services/`** owns application/business rules such as task ownership and pagination. This makes the rules reusable and testable without coupling them to Express.
- **`models/`** contains MongoDB/Mongoose schemas and indexes.
- **`validators/`** uses Zod so malformed request bodies/query strings fail with a predictable `400` response.
- **`middleware/auth.js`** verifies JWTs and loads the current user once per request.
- **`middleware/errorHandler.js`** gives the whole API one error-response format and handles validation, invalid Mongo IDs, duplicate keys, and unexpected errors centrally.

### Authorization model

The assignment requires ordinary users to see/manage their own tasks while admins can see all tasks. The implementation expresses that rule in one backend function:

```text
user  -> { owner: user._id }
admin -> { }
```

This is deliberately enforced on the **server**, not only hidden in the React UI. A user cannot bypass the UI and request another user's task by changing the URL.

### Frontend

- **React Router** provides `/login` and protected `/tasks` routes.
- **AuthContext** owns login/logout state and localStorage persistence.
- **Axios service** attaches the JWT to every API request through an interceptor.
- **TaskForm** is reused for create and edit, avoiding duplicate form logic.
- **TasksPage** owns list/filter/pagination state because those controls directly affect the API query.
- **TaskCard** is presentational and receives actions as props.

## 3. API design

### Authentication

`POST /api/auth/login`

Request:

```json
{
  "email": "user@example.com",
  "password": "User123!"
}
```

Response:

```json
{
  "token": "<jwt>",
  "user": {
    "id": "...",
    "email": "user@example.com",
    "role": "user"
  }
}
```

### Tasks

All task endpoints require:

```text
Authorization: Bearer <jwt>
```

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/tasks` | List/filter/search/sort/paginate tasks |
| GET | `/api/tasks/:id` | Get one accessible task |
| POST | `/api/tasks` | Create a task owned by current user |
| PATCH | `/api/tasks/:id` | Update an accessible task |
| DELETE | `/api/tasks/:id` | Delete an accessible task |

List query parameters:

```text
status=todo|in_progress|done
tag=frontend
search=dashboard
sortBy=createdAt|updatedAt|title|dueDate|status
order=asc|desc
page=1
limit=10
```

Example:

```text
GET /api/tasks?status=in_progress&search=frontend&sortBy=dueDate&order=asc&page=1&limit=5
```

Response shape:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 5,
    "total": 12,
    "totalPages": 3
  }
}
```

## 4. Data model

### User

- `email`: unique, normalized lowercase string
- `passwordHash`: bcrypt hash; never returned by normal user queries
- `role`: `user` or `admin`
- `createdAt`: generated by Mongoose

### Task

- `title`: required, max 200 characters
- `status`: `todo`, `in_progress`, or `done`
- `tags`: array of strings
- `dueDate`: nullable date
- `owner`: User ObjectId reference
- `createdAt`, `updatedAt`: generated timestamps

Indexes include owner/status/due-date combinations and a text index on `title` + `tags`. The goal is to keep the common authenticated list query efficient while supporting the required search feature.

## 5. Seed accounts

The seed script creates:

| Role | Email | Password |
|---|---|---|
| Admin | `admin@example.com` | `Admin123!` |
| User | `user@example.com` | `User123!` |

It also creates example tasks for both accounts.

These credentials are for local assignment/demo use only. Change them for any real deployment.

## 6. Local setup

### Prerequisites

- Node.js 20+
- npm
- MongoDB running locally, or a MongoDB connection string

### Install

```bash
cp .env.example server/.env
cp client/.env.example client/.env
npm install

> The repository uses npm workspaces, so this single command installs dependencies for the root, `server/`, and `client/`.
```

On Windows PowerShell, create the two files by copying `.env.example` manually if `cp` is unavailable.

Update `server/.env` if needed. At minimum:

```env
MONGO_URI=mongodb://127.0.0.1:27017/taskhub_lite
JWT_SECRET=use-a-long-random-secret
```

### Seed

```bash
npm run seed
```

### Run both apps

```bash
npm run dev
```

Then open:

```text
http://localhost:5173
```

Backend health check:

```text
http://localhost:5000/api/health
```

## 7. Tests

Backend tests cover:

1. Login returns a JWT for valid credentials.
2. `GET /api/tasks` returns correct pagination metadata and records.

Frontend tests cover:

1. The task page renders a mocked API task.

Run everything with:

```bash
npm test
```

The backend uses `mongodb-memory-server`, so its tests do not require a manually running MongoDB instance.

## 8. Security/performance decisions

- Passwords are hashed with **bcryptjs** using a work factor of 12 in the seed script.
- JWT authentication is required for every task route.
- JWT payload contains only identity/authorization data needed by the API.
- `helmet` adds common HTTP security headers.
- Login and task endpoints use rate limiting.
- Request bodies and query parameters are validated with Zod.
- Mongoose schema validation provides a second layer of data integrity.
- MongoDB indexes support owner/status/due-date lookups and text search.
- The API paginates at the database level instead of loading every task into memory.
- The frontend sends filters/sort/page to the backend rather than filtering the complete dataset client-side.
